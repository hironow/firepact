# 0008. `bytes` maps to the client SDK `Bytes`, not `Uint8Array`

**Date:** 2026-06-05
**Status:** Accepted

## Context

DESIGN.md §5.1's wire-type table maps Python `bytes` -> TypeScript `Uint8Array`.
That is correct for the **admin** SDK (`@google-cloud/firestore`, which returns
`Buffer`/`Uint8Array`), but firepact targets the **client** realtime SDK
(`firebase/firestore`, the whole point of the tool). The client SDK
returns and accepts a `Bytes` wrapper class for blob fields, not a raw
`Uint8Array`; you call `bytes.toUint8Array()` to get the array.

This was not caught by `tsc` (the generated `Uint8Array` type is internally
consistent) — it surfaced only when the runtime E2E read a real document from the
Firestore emulator and `value instanceof Uint8Array` was false (`instanceof
Bytes` is true). This is the class of wire-type mismatch that only a real
`onSnapshot` read can detect, and is the reason the E2E exists (DESIGN §1.2).

## Decision

Emit `Bytes` (imported from `firebase/firestore`) for `x-firestore-type: bytes`
in both the read and write views. This corrects the `Uint8Array` mapping in the
immutable seed DESIGN.md §5.1 for the client-SDK target. The live docs
(`docs/contract.md`) reflect `Bytes`.

## Consequences

### Positive
- The generated bytes type matches what the client SDK actually returns/accepts;
  runtime reads succeed.

### Negative
- Consumers handling raw bytes must call `.toUint8Array()` (one extra hop) — this
  is inherent to the client SDK, not a firepact choice.

### Neutral
- A backend using the admin SDK would see `Uint8Array`; firepact deliberately
  targets the client realtime SDK, so `Bytes` is the correct projection.
